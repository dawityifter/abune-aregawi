## 2. Database migrations

### Auto-run by the backend pipeline (`sequelize-cli db:migrate`)
Both live in `backend/migrations/`, are additive, guarded (existence checks + `.catch()`), and reversible (`down()`):

1. `20260708000000-create-zelle-email-queue.js` — creates `zelle_email_queue` (unique `external_id`, indexes).
2. `20260708000001-create-expense-memo-matches-and-bank-audit.js` — creates `expense_memo_matches`; adds `reconciled_source`, `reconciled_at`, `reconciled_meta` columns to `bank_transactions`.

The reconciliation-warning feature needs **no** migration (it upserts a row into the existing `church_settings` table, and degrades to the $50 default if that read fails).

### Recommended: run + verify migrations manually BEFORE pushing
The pipeline runs `db:migrate` on push, but running it yourself first lets you catch any migration error **before** the app restarts. Migrations are tracked in `SequelizeMeta`, so the pipeline's run afterward is a harmless no-op.

Run from a checkout at the exact commit you're deploying (your current local `main`):

```bash
cd backend
# Use your PROD DATABASE_URL. Add DB_SSL=true if prod Postgres requires SSL (managed PG usually does).
DATABASE_URL="<PROD_DATABASE_URL>" DB_SSL=true NODE_ENV=production npx sequelize-cli db:migrate --env production

# Confirm both new migrations show as "up"
DATABASE_URL="<PROD_DATABASE_URL>" DB_SSL=true NODE_ENV=production npx sequelize-cli db:migrate:status --env production
```

Expected `db:migrate:status` output includes:
```
up 20260708000000-create-zelle-email-queue.js
up 20260708000001-create-expense-memo-matches-and-bank-audit.js
```

> If you'd rather not touch prod by hand, you can skip this section and let the pipeline migrate on push — the migrations are idempotent and reversible. The manual step is purely for pre-verification.

## 3. ⚠️ Deploy ordering — the one real compatibility risk

Pushing this to `main` triggers **both** pipelines in parallel:
- `deploy-backend.yml` (on `backend/**`) → OCI VM, migrate + seed + pm2 restart.
- `firebase-deploy.yml` (on `frontend/**`) → Firebase Hosting.

The auth-hardening commit makes the **profile** and **dependents** endpoints require a Firebase token, and the matching **token-sending code is in the frontend**. Therefore:

- **New frontend + old backend → safe** (extra header ignored; missing `reconciliation` field just hides the new warning icon).
- **New backend + old (cached) frontend → 401** on profile load and dependents management, until the user's browser picks up the new frontend bundle.

Because both pipelines fire from one push and run in parallel, there is a short window where the backend may be new while a user still has the old frontend cached.

**Choose one:**

- **Option A — Timed push (simplest).** Push during a low-traffic window (e.g. late night). Watch both Actions runs to completion, then hard-refresh the app and confirm login works. Accept a brief window where a still-open old tab may need a refresh.

- **Option B — Frontend first, then backend (zero-risk).** Temporarily disable the backend workflow so only the frontend deploys, verify it's live, then re-enable and deploy the backend:
  1. In GitHub → Actions → **Deploy Backend** → `⋯` → **Disable workflow**.
  2. `git push origin main` → only **firebase-deploy** runs. Wait for it to finish; hard-refresh and confirm the app loads.
  3. Re-enable **Deploy Backend**, then Actions → **Deploy Backend** → **Run workflow** (`workflow_dispatch`) on `main`.

Recommended: **Option B** if any users may be active; **Option A** is fine for an off-hours deploy.

## 6. ZELLE_SYNC_ENABLED — keep it unset for the first days

The Zelle background poller only starts when `ZELLE_SYNC_ENABLED` is exactly `"true"`; **unset = disabled** (`src/jobs/zelleSyncScheduler.js`). The manual Zelle review screen and manual imports are unaffected — only the background poller is gated.

**To keep it unset: do nothing.**
- The server `.env` is **regenerated from the GitHub Actions secret list on every deploy**. `ZELLE_SYNC_ENABLED` is not in that list, so it is never written → stays unset → poller disabled.
- **Do not** hand-edit `.env` on the server — the next deploy overwrites it.

**To enable it later (after the first days):**
1. Add repo secret `ZELLE_SYNC_ENABLED = true` (Settings → Secrets and variables → Actions). Optionally `ZELLE_SYNC_INTERVAL_MINUTES` (default 15, min 5).
2. In `.github/workflows/deploy-backend.yml`, add it in three places (mirroring the other vars):
   - under `env:` → `ZELLE_SYNC_ENABLED: ${{ secrets.ZELLE_SYNC_ENABLED }}`
   - in the `envs:` comma list
   - an `echo "ZELLE_SYNC_ENABLED=$ZELLE_SYNC_ENABLED" | sudo tee -a .env > /dev/null` line
3. The `GMAIL_CLIENT_ID/SECRET/REFRESH_TOKEN` secrets are already wired, which the poller also requires.
4. Deploy — on restart the scheduler logs `Starting Zelle sync scheduler (every N minutes)`.

## 7. Optional one-time data cleanup (manual — not run by the pipeline)

`normalizeZelleMemoMatches.js` cleans legacy `zelle_memo_matches` and backfills `bank_memo_matches` so the email and bank-reconciliation flows share learned payer→member associations. It is **not** a schema migration and is **not** run by CI. The app works without it; running it just improves match suggestions. It is dedupe-aware/idempotent and its dependency (`bank_memo_matches`) already exists in prod.

Run once, after the deploy, on the server (or locally against prod):
```bash
cd backend
node src/database/migrations/normalizeZelleMemoMatches.js
```

## 8. Rollback

- **Schema:** each migration has a `down()`. To revert the last one:
  `DATABASE_URL="<PROD>" DB_SSL=true npx sequelize-cli db:migrate:undo --env production` (repeat for both if needed).
- **Code:** `git revert <sha>` (or reset `origin/main` back) and re-run the pipelines. The two new migrations are additive, so reverting the code without undoing the migrations is safe (unused table/columns).
- Restore from the DB backup only if a migration cannot be cleanly reversed.
